## User-visible goal

For each series, determine and display:

- the episode to resume;
- the number of episodes remaining;
- the total duration of those remaining episodes;
- the nearest expiration date among those remaining episodes.

The Excel report must therefore expose two new series-specific columns:

- `Épisode à reprendre`
- `Épisodes restants`

The existing `Durée` column must:

- keep its current behavior for movies;
- contain the TOTAL REMAINING duration for series.

The existing expiration-related columns must use the earliest expiration among the remaining episodes.

For movies:

- `Épisode à reprendre` is blank;
- `Épisodes restants` is blank;
- existing duration and expiration behavior remain unchanged.

## Meaning of "episode to resume"

`Épisode à reprendre` represents the first episode included in the remaining backlog.

Prefer a compact stable representation such as:

`S3E3`

If a trustworthy episode title is readily available from the episode catalog and fits the current report design cleanly, a representation such as:

`S3E3 — Episode title`

is acceptable.

However:

- do not require an episode title for the feature to work;
- do not invent a title;
- do not make additional per-episode requests just to obtain a title.

The season/episode coordinates are the important information.

Examples:

- series not started, first episode available: `S1E1`
- resume point at season 3 episode 3: `S3E3`

If the resume point cannot be determined safely, leave the value blank rather than inventing one.

## Core remaining-backlog rule

The current/resume episode counts as a FULL remaining episode, even when partially watched.

Example:

Playlist resume point:

- season 3
- episode 3
- `userProgress=64`

Remaining backlog begins with S3E3.

Count:

- S3E3 in full;
- every later episode in season 3;
- every episode in every later season.

Do NOT prorate the current episode according to `userProgress`.

Do NOT subtract already watched minutes from its duration.

Do NOT count:

- previous episodes in the current season;
- previous seasons.

## Playlist is authoritative for resume position

The playlist is the source of truth for the user's current/resume position when it provides usable information.

Prefer playlist values such as:

- `seasonID`
- `episodeID`
- `userProgress`

over potentially conflicting detail responses.

A real manually observed case had:

- playlist: S3E3, `userProgress=64`
- detailV5 resume action: S3E1

The playlist was correct for the user's actual resume position.

Therefore:

- usable playlist resume metadata wins;
- detailV5 must not override it.

If the playlist does NOT provide a usable resume season/episode, use existing detail/detailV5 metadata as a fallback.

Possible fallback sources observed during reverse engineering include:

- primary action content ID;
- primary action season ID;
- action tracking `seasonNumber`;
- action tracking `episodeNumber`;
- `URLEpisodesList`.

Do not assume tracking values always live at one fixed nesting level. Inspect the actual structures and reuse existing parsing patterns where possible.

## Fresh playlist state versus cached catalog state

This distinction is important.

The playlist contains current user state.

The episode API contains catalog/enrichment data.

Therefore:

- current resume position comes from the fresh playlist whenever possible;
- episode catalogs may be cached;
- changing the playlist resume position must take effect immediately even when episode catalog data comes from a fresh cache entry.

Do not freeze the user's resume point inside a catalog cache entry.

Example:

Run 1 playlist:

`S3E3`

Run 2 playlist:

`S3E5`

If the episode catalog cache is still fresh, Run 2 should reuse the cached catalog but calculate the backlog from S3E5.

No network request should be required merely because the resume point changed.

## Season discovery

A `/episodes` response can expose a `selector` describing available seasons.

Observed selector entries provide structured information including:

- season ID/content ID;
- season number;
- human-readable description;
- API-provided URL for the season.

The selector can therefore be used to discover later seasons without returning to a detail endpoint between every season.

Use structured fields and API-provided URLs.

Do not parse human-readable strings such as:

`Saison de 10 épisodes`

as the primary source of truth for the algorithm.

Those descriptions may be useful as secondary validation only.

## Season traversal

Once the resume season is known:

1. Obtain the episode catalog for the resume season.
2. Locate the resume episode.
3. Count that episode and all following episodes in the current season.
4. Discover later seasons.
5. Fetch/count every episode from later seasons.
6. Ignore earlier seasons.

Do not fetch earlier seasons merely to verify that they were watched.

Example synthetic series:

Available seasons:

- S1
- S2
- S3
- S4
- S5

Resume:

`S3E3`

Required catalogs:

- S3
- S4
- S5

Do not fetch S1 or S2 for backlog calculation.

Do not assume season IDs are contiguous.

Do not assume season numbers are necessarily contiguous.

Sort/traverse based on reliable structured season information.

## Alternative season metadata

Existing detail responses may also expose season information through legacy structures such as:

- `detail.seasons`
- `parentShow.seasons`

These can be used as sensible fallbacks if necessary.

However, once `/episodes` provides a usable selector with API-provided season URLs, prefer the clean episode-navigation path rather than repeatedly fetching detail pages.

## Resume episode matching

For the resume season, find the actual episode corresponding to the playlist resume point.

Prefer stable IDs:

- playlist `episodeID`
- episode catalog `contentID`

If stable IDs are unavailable or cannot be matched, use season/episode numbers as a sensible fallback when trustworthy.

Do not rely on array position alone.

Do not assume the first catalog item is episode 1.

If the resume point cannot be matched safely:

- do not silently count the whole season;
- do not fabricate a resume episode;
- degrade gracefully;
- log enough structured context to diagnose the issue;
- leave derived series values blank when correctness cannot be established.

## `Épisode à reprendre`

Once the resume episode has been safely matched, derive the report value.

Preferred minimum representation:

`S{seasonNumber}E{episodeNumber}`

Examples:

`S1E1`

`S3E3`

If an episode title is included, derive it from trustworthy catalog data.

Do not store the formatted `Épisode à reprendre` Excel string as canonical cache data.

It is presentation derived from:

- fresh playlist resume state;
- cached/fetched catalog metadata.

## `Épisodes restants`

Calculate:

remaining episodes in resume season
+
all episodes in later seasons

The resume episode is inclusive.

Example synthetic fixture:

Pikachu has:

- S3 containing E1 through E11;
- resume at S3E3;
- no later seasons.

Expected:

`Épisodes restants = 9`

If S4 contains 10 episodes and S5 contains 8 episodes:

Expected:

`9 + 10 + 8 = 27`

Do not use human-readable selector descriptions as a shortcut when actual episode contents are available.

The count should represent the episode entries actually included in the remaining backlog.

## Duration

The existing movie duration behavior must remain unchanged.

For series, calculate the total duration of all remaining episodes.

The partially watched resume episode counts at FULL duration.

Do not use `userProgress` to prorate duration.

Observed `/episodes` values include formats such as:

`57 min`

`1h02`

`1h31`

Implement a small robust parser for the actual observed duration-label formats.

Examples:

`57 min` -> 57 minutes

`1h02` -> 62 minutes

`1h31` -> 91 minutes

Do not make one detail request per episode to obtain numeric duration.

If a duration label cannot be parsed:

- do not invent a duration;
- handle the missing value explicitly.

Choose semantics that avoid presenting a knowingly incomplete total as a trustworthy complete duration.

Document the chosen behavior in `SPEC.md` and cover it with tests.

## Excel duration representation

Reuse the existing numeric Excel duration mechanism.

The workbook currently stores duration as an Excel numeric duration value rather than presentation-only text.

It uses a display format equivalent to:

`[h]" h "mm" min"`

Preserve this.

Examples:

Durations greater than 24 hours must remain summable/display correctly.

For series, the `Durée` cell should contain the TOTAL REMAINING duration.

Do not add a hidden "duration minutes" presentation column unless the existing architecture genuinely requires it.

## Expiration

For series, determine expiration using REMAINING EPISODES ONLY.

Collect valid `availabilityEndDate` timestamps from the remaining episode set.

Series expiration is:

the earliest valid expiration timestamp among remaining episodes.

Do not let:

- previous episodes;
- previous seasons;
- already-watched content

shorten the displayed expiration.

Example:

S3E1 expires tomorrow.

Resume point is S3E3.

S3E3+ expire next month.

The series expiration must be based on S3E3 and later, not S3E1.

## Expiration presentation

If no remaining episode has a valid expiration timestamp, preserve the existing unknown/no-expiration behavior.

Do not invent a date from a selector description or unrelated earlier episode.

## Series cache design

Series episode catalogs should be cacheable so repeated runs do not re-fetch every season.

The natural API granularity is one season per `/episodes` response.

A per-series/per-season cache representation is therefore likely appropriate, but inspect the existing cache architecture first.

Do NOT create an unrelated parallel cache subsystem if the current cache can be extended cleanly.

Use stable identities such as:

- brand/content ID;
- season ID;

as appropriate to the existing model.

Cache enough RAW catalog information to recalculate:

- resume episode;
- remaining episode count;
- remaining duration;
- remaining expiration

without another API request while the catalog cache is fresh.

This likely includes per-episode raw fields such as:

- stable episode ID;
- season number;
- episode number;
- raw duration minutes or safely parsed canonical duration;
- raw availability timestamp;
- optional episode title if needed for presentation.

Do not cache API URLs containing Hodor tokens.
